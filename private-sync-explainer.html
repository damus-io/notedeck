PrivateSync: one host-owned service for cross-device sync

Today each private-data app (headway, notebook) re-implements cross-device relay sync inside its own frame loop. That duplicates ~90% boilerplate and leaves a correctness hole. This is what folding it into one host-owned service looks like.

The two problems

correctness

The foreground gap

Sync is driven from each app's update(). Chrome only calls update() for opened apps (chrome.rs gated on bitset_get(&self.opened, i)).

So a headway/notebook CLI edit that lands in the embedded relay while its app was never opened this session syncs to the local board — but is never fanned out to the account's private relays. The per-app fix moved sync into update(), but that's still opened-gated: the caveat is structural, not incidental.

maintainability

Triplicated boilerplate

BoardSync / CanvasSync, their PollResponse, the poll state machine, and the whole update() fan-out sequence are ~90% identical between headway and notebook.

Every new private-data app copies it again and re-risks the render-vs-update detail. The app-specific surface is actually tiny — see below.

Where sync lives — now vs. proposed

The host seam already exists.

Notedeck::tick (crates/notedeck/src/app.rs:215) runs every frame regardless of the foreground app, right next to accounts.update(...). It already hosts the media-job, relay, nip05, and zap pollers. PrivateSync becomes one more owned field on Notedeck, polled here — not in Chrome's per-app loop.

The two directions of sync

inbound

Scoped subscription

A scoped sub of authors([me]).kinds(union_of_registered_kinds) against the private relays — a NIP-77 full-history catch-up and a live REQ. Edits made on another device land in nostrdb.

generalizes PrivateRelaySync::update — private_sync.rs:150

outbound

Fan-out of unseen notes

Poll the service's own ndb sub over the same merged filter; call fan_out_unseen_notes(...) to publish each freshly-ingested note to the private relays it hasn't been seen on yet (per nostrdb's note.relays()). A note pulled in by inbound sync is not echoed back out.

reused unchanged — private_sync.rs:66

Why this isn't a sync loop.

The seen-on check skips relays a note already carries. Even if it misses (e.g. a relay-url normalization mismatch), nostrdb never re-reports an event id it already holds — so a redundant publish can't spiral. The service's ndb sub is independent of each app's rendering sub: two cheap subs over overlapping filters is fine, and sync no longer piggybacks on app polling.

What's actually app-specific

Per app, only three things genuinely differ. Everything else is boilerplate that collapses into the service.

1 · kinds

HEADWAY_KINDS / NOTEBOOK_KINDS + a limit. Static consts — known at roster-wiring time.

2 · view domain

The reducer / view types (BoardView, CanvasView) that fold events into rendering. Stays in the app.

3 · auto-seed

The app's default-document seed. Stays in the app; the service fans out the seed note on its next poll.

Open question: how do apps register?

Option A — per-frame handle

A &mut PrivateSyncRegistry on AppContext; apps call idempotent register(scope) on first update()/render().

✕ still couples registration to the app having been opened — the exact gap we're fixing.

Option B — static at roster-wiring ✓ leaning

Register when Chrome wires apps into the NotedeckApp roster — once at construction, no per-frame call.

✓ decouples the service from whether an app was ever opened, which is the whole point. Kinds are static consts, so they're known then.

A scope is roughly { app: &'static str, kinds: &'static [u64], limit: u64 }. Open sub-question: one merged sub (union of kinds, simpler, fewer subs) vs. one sub per scope (cleaner isolation). Leaning union unless kinds collide semantically.

dave is the outlier — don't fold it in

dave syncs PNS-encrypted session state (kind-31988 wrapped in kind-1080) keyed on a derived PNS author pubkey, with bespoke wrap/unwrap and its own dedup state. It shares only the kind-10013 relay source. Converging it needs a per-scope outbound: Plaintext | Pns(keys) transform + derived-author sub — a follow-up that aligns with the planned nostrdb-net / agentium-core sync-engine extraction. This refactor does not block on dave.

Migration plan

  1. Add the service. New PrivateSync + registry in notedeck core; poll in tick. Generalize PrivateRelaySync's inbound-sub logic to the merged filter.
  2. Register headway + notebook kinds via the chosen seam (leaning static / Option B).
  3. Delete per-app sync driving. Revert the update()-based fan-out; keep the fan_out_unseen_notes helper (the service calls it). Apps' BoardSync/CanvasSync shrink to a render-only reducer poll.
  4. Test. Host-level test that a CLI-ingested note for a never-opened app still fans out; keep the seen-on dedup unit tests.
  5. Later (separate card). dave encryption-adapter convergence.

Risks to watch

  • Blast radius. Touches core host tick — higher risk than the per-app fix. Review that we don't regress the dedup / log-throttle behavior in PrivateRelaySync (it only re-declares + logs on an actual account/relay-set change, not every frame).
  • Merged filter collisions. If two apps' kinds overlap semantically, a union sub blends them; per-scope subs isolate. Default to union.
  • Auto-seed ordering. Seed still runs in-app and writes locally first; the service fans it out on the next poll. Correct, but the ordering should be asserted.
